pymon is a monitoring stack made of three small pieces: an agent that runs on your hosts, a server that evaluates the rules you actually care about, and a web UI that makes the result obvious. No SaaS, no per-host pricing, and no telemetry leaving your network.

The stack

Three pieces, one system

Each part is useful on its own and boring on purpose: small surface area, plain HTTP between components, and a configuration format you can read.

pymon-agent

The agent

A single Python file that installs itself as a service, downloads its assigned plugins from the server, runs each one in its own thread and pushes the results back every few seconds.

It refreshes its plugin list and config on a timer, reports its own version, updates itself, and carries a watchdog that restarts it if ingest stalls. Plugins keep their state in a small file, so derived values survive a restart.

pymon-server

The server

Flask and SQLAlchemy behind a plain REST API. It stores incoming metrics, evaluates your rules, maintains the alarm lifecycle, dispatches notifications and shell executors, and serves the plugin source that the agents pull.

SQLite is the default; PostgreSQL is a single environment variable away, including a one-shot, id-batched migration of an existing database. A built-in Swagger UI documents every endpoint.

pymon-web

The web UI

Svelte 5 and Vite behind nginx, styled with a glassy dark and light theme. Dashboards group panels into one- or two-column grids with per-panel comments, filters, a problem-only view and full screen for both chart and table.

Installable as a PWA with web push, and it ships an in-browser plugin editor with syntax checking so you never leave the UI to fix a plugin.

Architecture

Nothing clever, just clear

Agents push metrics and pull plugins. The server never dials out to your hosts, which means the agent is the only component that needs inbound access to anything — and the only one you have to trust with a command.

Features

The parts that actually matter day to day

A rule engine, not a threshold field

Four evaluation scopes, nine conditions and three fire modes per rule — so "average over 5 samples", "3 of the last 10", "the delta grew" and "nothing arrived for 300s" are all first class.

Store less, alert the same

Unchanged values are discarded inside a heartbeat window and only written when something actually moves. Long-lived stable metrics cost almost nothing, while ratio rules still count every sample they would have seen.

Match any metric

A rule targets one exact metric name, a full-match regular expression such as temperature_.*, or * for everything a plugin reports.

Alerts where you already are

ntfy, e-mail via SMTP, browser web push and Twilio voice calls. Every target is testable from the UI, and the SMTP password stays in an environment variable instead of the config file.

Executors, on your terms

Any rule can run a shell command, either on the server or pushed to the agent that raised the alarm, with {rule_id}, {agentid}, {metric}, {value} and more substituted in.

Planned downtime stays quiet

Blackout windows suppress alarms or only the notifications, scoped by weekday and time, with overnight ranges supported. Target specific rules, agents or groups — or go global for a maintenance night.

Dashboards worth looking at

One- or two-column grids, sticky controls, per-panel comments in an info modal, a text filter and a problem-only view. Panels open full screen as chart or table, capped so a wide query stays responsive.

Alarms with context

Detail view shows nearby same-rule alarms on both sides of the current one with their signed distance, per-rule incident statistics instead of a useless alarm-to-alarm median, plus snoozes and acknowledgements.

Scheduled work, not just alerts

crontab-style tasks are evaluated on the server in your local timezone and handed to the right agent exactly once. The agent runs the command under a timeout and reports exit code and duration as alertable metrics.

Retention you stop thinking about

A nightly job deletes metrics past the retention period in small batches, releasing the write lock between batches so ingest keeps flowing, and reports what the last run removed.

SQLite or PostgreSQL

The default is a single SQLite file — ideal for a homelab. Set one variable to move to PostgreSQL, and let the server migrate an existing database in id-batched steps at startup.

Boring where it counts

JWT sessions for the UI, per-agent API keys compared in constant time, login rate limiting, plugin paths checked against a strict allowlist, executor commands run without a shell, and atomic config writes.

Rule engine

Four ways to decide something is wrong

The scope decides what a rule looks at, the condition decides what counts as a violation, and the fire mode decides how often you get told.

1 Evaluation scopes

single
Evaluate each individual measurement.
moving_avg
Average of the last window_size measurements.
count_ratio
How many of the last window_size measurements violate the threshold. Fires at min_violations.
change
Delta between current and previous value; the threshold is compared against the delta.

2 Conditions

gtge ltle eqne betweenoutside no_data

Range conditions use threshold_min and threshold_max. no_data fires when a metric that has been seen at least once stops arriving for threshold seconds — useful for dead lines and silent sensors that would otherwise look perfectly healthy.

3 Fire modes

single
At most one open alarm per agent, plugin and metric. Sibling plugins each open their own alarm instead of swallowing each other.
multi
A new alarm on every violation.
replace
Acknowledge the open alarms for that combination, then raise one fresh alarm.

auto_close works with all three: the moment a rule stops triggering, its open alarms are acknowledged automatically.

Scope rules to agents the way you expect. An empty agent list with agents_mode: "exclude" means "applies to everyone". Switch to include to whitelist, or keep exclude with a list to blacklist — the same rule structure covers a global threshold and a host-specific exception.
Plugins

19 collectors, and you can write the twentieth

A plugin is a Python file that exposes a run(config) function and returns a flat dictionary of metric values. The server ships them, the agent downloads them, and the web UI lets you edit them with syntax checking.

vigor130

A DSL line, not just "up" or "down"

Scrapes the authenticated status page of a DrayTek Vigor 130 and reports sync rates, SNR, attenuation, line state, error counters and system uptime per direction. A persistent state file turns raw counters into deltas and per-hour rates, and distinguishes a line resync from a modem reboot.

Credentials and session tokens are never emitted, and a failed scrape only lowers a success flag — it can never fabricate an outage.

docker_host

Containers you can actually reason about

CPU, memory, pids, block IO and network counters per container, plus image update checks. Swarm task containers are tracked at service level, because their restart during a rollout is expected behaviour rather than an outage.

Unhealthy containers are skipped by the update check, and hosts whose images ship no HEALTHCHECK would silently lose coverage — the count of skipped containers is reported instead of vanishing.

Self-host

Two commands and you are monitoring

Images are published per release and also track latest. Run the server and the web UI, point an agent at them, and you are done.

server 
# stores its database in the pymon-data volume
docker run -d --name pymon-server --restart unless-stopped \
  -p 5000:5000 \
  -v pymon-data:/data \
  -e PYMON_CORS_ORIGINS="https://pymon.example.com" \
  ghcr.io/mcfetz/pymon-server:latest
web 
# nginx proxies /api/* to the server, no CORS juggling
docker run -d --name pymon-web --restart unless-stopped \
  -p 80:80 \
  -e PYMON_API_URL="http://pymon-server:5000" \
  ghcr.io/mcfetz/pymon-web:latest
agent — run on every host you want to watch 
# host networking + pid:host give accurate interface and process metrics
docker run -d --name pymon-agent --restart unless-stopped \
  --network host --pid host \
  -v pymon-agent-plugins:/app/plugins \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e PYMON_SERVER="https://pymon.example.com/api" \
  -e PYMON_AGENTID="my-host" \
  -e PYMON_API_KEY="your-agent-api-key" \
  ghcr.io/mcfetz/pymon-agent:latest
Change the default credentials before you expose the UI. They exist so a fresh install is reachable, not so they can stay. Set PYMON_ADMIN_PASSWORD on the very first boot, or change it from the Account page afterwards. Cross-origin requests are blocked by default, so a missing PYMON_CORS_ORIGINS is the most common reason the UI shows network errors right after login.
